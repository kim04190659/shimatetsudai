## 1. 全体構成（3つの独立したNext.jsアプリ）

しまてつだいは、単一のアプリではなく、役割の異なる3つの独立したリポジトリ・Vercelプロジェクトで構成される。共通のデータストアとしてNotionを使い、必要な箇所のみSupabaseを併用する。

| リポジトリ | 役割 | 本番URL | Vercelプロジェクト |
|---|---|---|---|
| `shimatetsudai` | 会社サイト・意思決定支援ダッシュボード・分室ページ | shimatetsudai.vercel.app | prj_KWnCo1bXnjNGv2Gb1iCxQDiYUFlm |
| `shimatetsudai-issue-cardgame` | しまのみんな会議（カードゲーム） | shimatetsudai-issue-cardgame.vercel.app | prj_oYgfvm7Vth6BlsrKrXJlYX3CsxH0 |
| `shimatetsudai-tetsudatte` | てつだって拡張版 | shimatetsudai-tetsudatte.vercel.app | prj_uiVu6BIikwX644hvz6BzUIk3u0F8 |

いずれもGitHub（kim04190659組織）と連携し、Vercel上でNext.js 16系・App Router・TypeScriptで構築している。既存の個人向け「てつだって」（tetsudatte リポジトリ、Next.js 14・Pages Router、本番稼働中）とは完全に独立しており、統合にあたってはVercelのMulti-Zones機能の採用を検討したが、既存アプリのURL・QRコード・利用者マニュアルへの影響を避けるため見送り、新規リポジトリでの再実装を選んだ。

## 2. shimatetsudai（会社サイト・意思決定支援基盤）

### 2.1 技術スタック

- Next.js 16.3.0（App Router、Turbopack）
- React 19.2.8 / TypeScript 5
- Tailwind CSS 4
- `@notionhq/client` 5.25.2（Notion API連携）
- `bcryptjs`（パスワードハッシュ化）
- Vercelにホスティング（Node.js runtime）

### 2.2 ディレクトリ構成（抜粋）

```
src/
  app/
    branches/[slug]/          分室ページ（自治体・商工会・観光協会を横断表示）
    jichitai/, shoukoukai/, kankoukyoukai/   主体別トップページ・分室一覧
    dashboard/[slug]/         意思決定支援ダッシュボード（パスワード保護）
    case-studies/             静的HTMLダッシュボード（りとけい等の旧版）
    tools/[slug]/             3ツール紹介ページ
    contact/                  お問い合わせ・ダッシュボードトライアル申請
    api/
      tenant/[slug]/opinion/         意見投稿API（汎用・パスワード不要）
      branch/[slug]/auth/            分室ページ用パスワード認証API
      dashboard/[slug]/auth,refresh  ダッシュボード用パスワード認証・更新API
      contact-chat/                  AIによる問い合わせ対応チャット
      dashboard-trial-application/   ダッシュボード試用申請の受付
  components/                 OpinionForm・BranchPasswordGate 等のクライアントコンポーネント
  lib/
    tenants.ts                TENANTS_CONFIG（環境変数）からテナント設定を読む
    branches.ts / shoukoukai.ts / kankoukyoukai.ts   分室データ（ハードコード分＋テナント設定からの自動合成分）
    tenantDashboard.ts        テナント別ダッシュボードデータのキャッシュ取得
    tenantDashboardHtml.ts    汎用ダッシュボードHTML生成（6〜8タブ構成）
    tenantAuth.ts             HMAC-SHA256署名付きセッションCookieの発行・検証
    notion.ts                 Notion APIラッパー（Issue・PositionRecord・EvidenceRecord等の取得/作成）
    regionalGoal.ts           島の上位ゴールと各論点の貢献・リスクの対応表
    llm/                      LLMプロバイダ抽象化層
```

### 2.3 テナント設定とマルチテナント構成

- `TENANTS_CONFIG` という1つの環境変数（JSON配列）に、団体ごとの設定をまとめて持つ。各エントリは `slug`・`issuePageId`・`positionRecordDataSourceId`・`passwordHash`・`status` に加え、`publicName`・`publicKind`（jichitai/shoukoukai/kankoukyoukai）・`gatesBranchSlug`（分室ページ自体をパスワード保護する場合に指定）などのフィールドを持つ。
- `getAllBranches()` / `getAllShoukoukaiBranches()` / `getAllKankoukyoukaiBranches()` が、ハードコードされた分室データと、TENANTS_CONFIGから自動合成した分室データをマージして返す。これにより、新しい島・団体を追加する際にコード変更なしで `/branches/[slug]` 等のページが自動生成される（`dynamicParams = true` を設定し、`generateStaticParams` に含まれないslugもオンデマンドで動的レンダリングされる）。
- パスワード保護は2段階ある。
  1. **ダッシュボード単位**（従来）: `/dashboard/[slug]` にパスワードを設定
  2. **分室ページ単位**（2026-08-22追加）: `/branches/[slug]` 等のページ自体にパスワードを設定（`gatesBranchSlug` で指定）。実装は `cookies()`（`next/headers`）をページ内で呼び出し、`tenantAuth.ts` の署名検証に失敗した場合は `<BranchPasswordGate>` を表示する。Cookie名は `branch:${slug}` のように名前空間を分け、ダッシュボード用セッションと衝突しないようにしている。

### 2.4 意思決定支援ダッシュボードの生成方式

- `unstable_cache`（`next/cache`）でテナントごとにキャッシュタグ（`dashboard-${slug}`）を付けてキャッシュする。
- 拠点スタッフが「最新の議事録で更新」ボタンを押すと、`/api/dashboard/[slug]/refresh` がNotionから最新データを取得し、LLMで文章を再生成し、`revalidateTag` でキャッシュを更新する。
- ダッシュボードHTMLは `tenantDashboardHtml.ts` が生成する。人手で調査した「自治体目標」「提案内容」「類似事例」「補助金」等のタブは `tenantStaticContent.ts` に団体ごとに登録された静的コンテンツを使い、未登録の場合は「調査中」の案内を正直に表示する（実データが無いのに生成AIで埋めることはしない設計）。
- 過去のバージョン管理（v1〜v7等）は、静的HTMLファイル（`public/case-studies/*.html`）として履歴を残す運用も一部で併用している（りとけい版など）。

### 2.5 LLMプロバイダ抽象化層（`src/lib/llm/`）

- `index.ts` / `types.ts` / `providers/anthropic.ts` / `providers/openaiCompatible.ts` で構成。
- 環境変数 `SUMMARY_LLM_PROVIDER`（既定値: `anthropic`）で使用モデルを切り替えられる。
- 対応プロバイダ: `anthropic`（Claude、既定・最も安定）、`sakura-llmjp`（さくらインターネットAI Engine経由、研究機関開発のオープンな国産モデル llm-jp-3.1-8x13b-instruct4）、`sakura-cotomi`（同API経由でNECの国産モデルCotomiを想定、2026-08時点では「This model is not available」で利用不可）、`sakura-plamo` 等。
- 選択したモデルの呼び出しが失敗した場合は、自動的に既定の安定モデル（Anthropic）にフォールバックする。これにより、国産モデルを積極的に試しながらもサイトの機能自体が止まるリスクを避けている。

### 2.6 意見投稿の2つの方式

1. **汎用意見投稿API**（`/api/tenant/[slug]/opinion`）: パスワード不要。`{stance, content}` を受け取り、対象テナントのPositionRecordに匿名で1件登録する（`src/lib/notion.ts` の `submitOpinion()`）。分室ページに自動で埋め込まれる `OpinionForm` コンポーネントから呼ばれる、自由記述ベースの簡易版。
2. **しまのみんな会議（本物のカードゲーム）**: 別リポジトリのアプリに `cardGameUrl` でリンクする方式。屋久島・渡名喜村・りとけい・みなも島など、より作り込まれた体験を提供したい論点はこちらを採用する。当初はしまてつだいリポジトリ内にカスタムのカード選択UI（`OpinionCardGame`）を自作したが、「サイトが持つ本来のツールを使うべき」という判断で撤去し、本物のしまのみんな会議アプリ側にゲーム設定を追加する方式に統一した（2026-08-23）。

## 3. shimatetsudai-issue-cardgame（しまのみんな会議）

### 3.1 技術スタック

- Next.js 16.1.0（App Router、Turbopack）
- React 19.2.3 / TypeScript 5
- Zustand（状態管理）、TanStack Query、Framer Motion、next-pwa（PWA対応）
- `@anthropic-ai/sdk`（AIによる意見要約）
- `@supabase/supabase-js` + Prisma（利用ログ・カード選択履歴等の保存）

### 3.2 ゲーム設定とデータフロー

- `src/data/games/games.json` に全ゲームの一覧（id・name・description・file・tags）を登録。
- 論点ごとの詳細設定は `src/data/games/issue-*.json` に個別ファイルとして持つ。各ファイルは以下を含む。
  - `cardCategories`: 4カテゴリ（perspective/value/concern/conclusion、トランプのスート♠♣♦♥に対応）、各13枚・計52枚
  - `cards`: 各カードのID・名称・説明・アイコン絵文字・詳細
  - `inputFields`: 自由記述欄の設定（バリデーション含む）
  - `notion`: 連携先の `issuePageId` と `positionRecordDataSourceId`（しまてつだい側で作成したNotion DBを直接指定する）
  - `promptSettings`: AI要約用のシステムプロンプトテンプレート
- ルーティングは `/games/[gameId]/{cards,input,output,evaluation}` の4ステップ構成。
- 送信時は `src/app/api/notion/submit-position/route.ts` が、選択されたカード内容と自由記述・AI要約をまとめてNotion PositionRecordに1件のページとして直接POSTする（`NOTION_API_VERSION = '2025-09-03'`）。結論カードの文言から `stance`（賛成/反対/条件付き賛成/保留）を推定するロジックを持つ。
- Notion連携先（`issuePageId` / `positionRecordDataSourceId`）はゲームJSON側で個別指定でき、未指定時は環境変数の既定値（屋久島町）にフォールバックする設計になっている。これにより、1つのアプリで複数団体・複数論点のゲームを同時に運用できる。

### 3.3 Supabase

- `users` テーブル・`card_history` テーブルを持ち、RLS（Row Level Security）で匿名アクセス可能な設定にしている（利用ログ・フィードバック評価の保存用）。個人が特定できる情報は保存しない設計。

## 4. shimatetsudai-tetsudatte（てつだって拡張版）

### 4.1 技術スタック

- Next.js 16.3.1（App Router）
- React 19.2.8 / TypeScript 5
- `next-auth`（Auth.js v5 beta）によるGoogle OAuth認証
- `@notionhq/client`（データ永続化はNotion DBに寄せる方針）
- `nosleep.js`（音声入力時の画面スリープ防止）

### 4.2 データ設計

既存の「てつだって」（`tetsudatte_usage_log` / `tetsudatte_health_log`）とは完全に分離した、拡張版専用のNotion DBを新規に持つ。

- **TetsudatteRecord** — 声の聞き取り・写真ライフログの記録本体
- **TetsudatteSharePermission** — 利用者から支援者への閲覧許可（同意ベース共有）
- **TetsudatteAnnouncement** — 地域のアクティブな論点への意見登録を促すお知らせ
- **TetsudatteUserProfile** — 利用者プロフィール

## 5. 外部サービス・インフラ共通事項

- **Notion**: 全アプリ共通のデータストア。MCP経由（`notion-create-database` 等）でスキーマ定義・データ登録を行い、Notion API（`@notionhq/client` またはfetch直叩き）で各アプリから読み書きする。
- **Vercel**: 3リポジトリそれぞれを個別プロジェクトとしてデプロイ。GitHub連携による自動デプロイ、Runtime Logs/Errors機能で本番エラーを調査できる（Vercel MCP経由）。
- **さくらインターネット AI Engine**: 国産LLM（llm-jp-3.1-8x13b-instruct4、月3,000回まで無料枠あり）へのAPIアクセスに使用。Cotomi対応も同APIを経由させる設計で、Cotomi側と協議すれば切り替え可能な構成にしてある（2026-08時点ではCotomi自体は「利用不可」の状態）。
- **e-Stat / RESAS**: オープンデータの取得元。生成AIへの指示ベースで検索・取得し、EvidenceRecordとして登録する。

## 6. 運用上の注意点・既知の制約

- 新しく作成したNotionページ・データベースは、API経由で作成しただけでは自動的にアプリ連携用の統合（インテグレーション）に共有されない。新しい団体・分室を追加するたびに、Notion側で対象DB・ページへの「接続を追加」を手動で行う必要がある（この運用上の注意点は、実際にみなも島公開後の500エラーを通じて判明した）。
- `unstable_cache` は、コードの変更（レスポンス型の変更等）があってもキャッシュされた古いデータをそのまま返すことがあるため、フィールド追加時は呼び出し側で `?? []` 等の防御的な参照が必要。
- Next.jsの `cookies()` をページコンポーネント内で呼び出すと、その分岐条件（例: パスワードハッシュが設定されているか）が真になった時点でNext.jsが該当パスを動的レンダリングに切り替える。ビルド時に環境変数（TENANTS_CONFIG）が存在しないと、この分岐が働かず静的化されてしまう点に注意が必要（ローカルビルドとVercel本番ビルドで挙動が異なりうる）。
