## 統合方式の選択肢

### 方式1: 物理統合(1つのNext.jsアプリにマージ)
- 会社サイトの `/tools/tetsudatte` に、てつだってのコードをそのまま移植する
- Pros: URL・技術スタックが完全に一体化
- Cons: Next.js 14→16、Pages Router→App Routerへの全面移行が必要。認証・PWA・Service Worker・Web Pushなど本番稼働中の仕組みを作り直すことになり、破壊リスクが高い。てつだって側のCLAUDE.mdで定めたシナリオDoD運用も一時的に崩れる

### 方式2: Vercel Multi-Zones(推奨)
- 会社サイトとてつだってを、それぞれ独立したリポジトリ・独立したVercelプロジェクトのまま維持する
- 会社サイト側の `next.config.ts` に rewrites を設定し、`/tools/tetsudatte/:path*` を `tetsudatte.vercel.app` にプロキシする(Next.jsのMulti-Zones機能)
- ユーザーからは同一ドメイン配下の1サイトに見えるが、実装・デプロイ・バージョンアップのタイミングは完全に独立
- Pros: 本番稼働中のてつだってに一切手を入れずに済む。両者を別ペースで開発できる
- Cons: 完全な一体感(共通ヘッダーなど)を出すには、てつだって側にも多少のデザイン調整が必要

### 方式3: リンク遷移のみ(最小構成)
- 会社サイトのツール紹介ページから外部リンクとして `tetsudatte.vercel.app` に飛ばすだけ
- Pros: 実装コストが最小
- Cons: URLが変わりブランドの一体感が薄い

## 【2026-08-15 確定】方式2(Multi-Zones)は見送り

Multi-Zonesを実現するには、てつだって側に `basePath: '/tools/tetsudatte'` の設定が必要になる。この設定はアプリの全URLに影響するため、`tetsudatte.vercel.app/connect` のような現行の本番URLがすべて変わってしまい、すでに配布済みの「てつだって_デモ用QRコード」「てつだって_利用者マニュアル」(横浜デモでも使用)が無効になる。難聴・高齢の利用者向けツールであり、この影響は避けるべきと判断し、方式2は見送りとした。

## 【確定方針】既存てつだってはそのまま維持 + 新しい拡張版アプリを別途開発

- **既存の「てつだって」(GitHubリポジトリ `kim04190659/tetsudatte`、Next.js 14・Pages Router・本番稼働中)には一切手を加えない。** URL・QRコード・利用者マニュアルはすべて現状のまま。
- 会社サイトのモノレポ内(`/tools/tetsudatte`)には、**新しく作り直す拡張版アプリ**を実装する。
  - 対象を「難聴・高齢者個人への支援」から「島全体のことを考えたアプリケーション」へ拡張する
  - 既存てつだってのシナリオ先行原則・Will/Loop/Signalの開発思想は参考にしつつ、機能・スコープは新規に設計する
  - 技術スタックは会社サイトに合わせてNext.js 16 / App Router / TypeScriptとする
- 会社サイトの「てつだって」紹介ページでは、当面は既存てつだって(個人向け・現行版)を外部リンクで案内しつつ、拡張版アプリの開発状況を随時反映する運用とする
